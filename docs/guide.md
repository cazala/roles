# Guide

Run `npm ci && npm run build` to create `dist/index.html`. Run `npm run fork` with an archive-capable `FORK_URL`, then `npm run dev -- --anvil http://127.0.0.1:8545` to use the development-only Anvil wallet. The normal `npm run dev` has no test wallet. Never use Anvil's public test keys with real funds.

Home searches addresses and labels saved in this browser. Paste a Safe or Roles address or a mainnet `.eth` / `.wei` name and select Open: it opens at its URL (`#/<address>`), and if it needs something first, the page says so, as in safe.wei. Without a wallet it asks you to connect one (one button per wallet found; with just one, a fresh Open connects it right away), then opens the address. When the link names a chain (`?chain=`, as saved addresses open) and your wallet is on another, it offers **Switch to …**. An address you saved only on another chain may exist on this one too, so it offers the switch and **Open it on … anyway**. A name opened on another chain offers Ethereum, where names resolve. **Settings** (the gear in the header) holds two optional things, kept in this browser: **RPC endpoints**, where every read on an endpoint's chain goes instead of your wallet's RPC (paste a URL such as Alchemy or Infura; its chain is detected; signing always stays in your wallet), and an **Etherscan API key**, with which a modifier's history comes from Etherscan's index in a few requests (roles.wei checks each event and its block against the chain, but trusts Etherscan to return all of them: a missing event would hide a permission). Connect your browser wallet when prompted, or **WalletConnect** to use a wallet on your phone: scan the QR code with the wallet app and approve; signatures and transactions are then confirmed on the phone, and the account menu offers **Switch to …** for every network the phone approved. The account button shows the chain and your account, by its .wei or ENS name when it has one (Ethereum); its menu has Switch wallet and Disconnect. Names use only onchain resolution through the wallet. Label addresses with the tag button; Remove has a local Undo action. Saved entries remember their chain.

Opening a Safe lists its enabled modules. Open a supported Roles 2.1.1 proxy to scan its history and inspect roles, members, targets and raw conditions. The scan runs in bounded windows, caches completed work, keeps going until it catches up, and can be paused and resumed. It needs no archive RPC: the start is the modifier's deployment block, found from its code at past blocks where the RPC keeps them, else from its `RolesModSetup` event (emitted once, when it is deployed), which is in the logs every node keeps. ⋯ → Start from block accepts a start block; a history that contains the setup event is complete, and one that starts after it is explicitly read-only. ⋯ → Clear cached history discards cached events and scans again. Faulty and unknown versions remain identified without editing. All deployment/name changes on mainnet belong to the owner. When your wallet's RPC does not keep that history (errors like "historical state … is not available" or "pruned history unavailable"), the scan continues through WalletConnect's RPC, and the status line says which RPC served it. What was read is kept in this browser: the events scanned so far (the next visit only reads new blocks) and the modifier's deployment block, which never changes (it survives clearing the cached history). If the chain reorganized the latest blocks, only the last 1,000 blocks are scanned again. The history shows as one sync bar: the status, then the one action that fits it (Pause while scanning, Resume when paused, Retry after an error, Refresh when done), with a thin progress line while it scans; ⋯ holds the rare options, Start from block and Clear cached history. Once the history is complete the bar recedes to a muted line. While it scans, the status shows the share of blocks done, the events found and a time estimate from the scan's own pace; without an Etherscan key, it ends with a highlighted **Add an Etherscan key** to load instantly (it opens Settings), since the history then loads in a few seconds.

A role's page has **Permissions** and **Members** tabs. Permissions has one card per target contract (its name, full address and clearance: All functions, Scoped · N functions, or Revoked) listing each allowed function with its signature, its selector, and warnings when it may send ETH or delegatecall. Conditions read as a table, one row per parameter (Parameter · Type · Condition · Value), with AND / OR / NOR groups drawn as labelled brackets, nested tuples and arrays indented, allowances linked, and parameters without a condition shown as any value. Names come from an ABI you give (the card's ⋯ → **Add contract ABI…**: **Upload .json**, a compiler artifact from Hardhat, Foundry or Truffle, or a plain ABI, or paste it; the contract name comes from the artifact or the optional name field; the option is hidden when Etherscan already has the verified ABI), else Etherscan's verified source when a key is set in Settings (the contract name too; the card says when Etherscan has no verified source), else standard interfaces (ERC-20, ERC-4626, WETH); a name is used only when it matches the function's selector, which is what executes, and the card says where the names came from. Values are decoded by the ABI type when known, otherwise shown exactly as encoded; with an Etherscan key, addresses (in values and in Members) show the contract's name next to them, muted (e.g. GPv2VaultRelayer, or SafeProxy for a Safe); Exact conditions shows the raw tree. Unknown operators remain explicitly raw. Without a supplied ABI, parameters are numbered and comparison values stay in their exact encoding; the app never guesses token units or parameter names. The Allowances tab reads storage at the displayed block, shows exact balances/refill periods and lists roles that reference each allowance. Refresh to read a newer block.

Complete scans are editable, in place: each thing carries its own actions. **+ Add target** and **+ Add member** sit next to the tabs. A target card's ⋯ has Add function, Allow all functions (or Execution options and Only configured functions when it allows all), the contract ABI, Copy address and Revoke target; **+ Add function** at the bottom of a scoped card lists the contract's write functions from its ABI (yours or Etherscan's) that the role does not have yet, to allow with any parameters or with conditions, or takes a typed signature or selector. A function's ⋯ has Edit conditions (opened on that function, typed from its ABI), Allow any parameters, Execution options and Revoke function; a member's ⋯ has Make this their default role, Copy address and Remove member. What the draft changes is marked where it is: New or Changed on the card or row, and a revoked target, function or removed member struck through in place with **Restore**. One bar above the role counts the pending changes, with Undo, Discard and **Review changes**, which lists the calls before applying them. Every review shows full addresses, decoded arguments, calldata and signatures. Widening permissions and authority changes carry explicit warnings. Drafts stay in this browser until they are applied or discarded, and Undo restores the preceding draft state.

When the modifier owner is the connected account, Apply sends each configuration call separately after simulating it and checking that the onchain configuration has not changed. Each receipt updates the baseline, so an interruption preserves only the calls that remain. When a Safe owns the modifier, choose a safe.wei gateway and current or later nonce, then prepare the verified `#tx=` link. The app validates the Safe transaction hash returned by the Safe and includes each readable call signature; copy the link or open it for the owners to review and approve in safe.wei.

If the owner is neither the connected account nor a readable Safe, roles.wei says so before editing. The generated configuration calls remain fully inspectable in Review changes, but the app does not pretend it can submit them for an unknown owner. On narrow screens, a fixed pending-changes button stays above the browser edge until the draft is reviewed or discarded.

Creating a modifier is a four-step wizard, one step at a time with Back / Next: **Setup** (owner, avatar and target are this Safe, recommended; Customize to change them, with a warning for anything else; the salt under Advanced), **How** (with the Safe in one transaction, recommended, or deploy now from your wallet and enable later), **Review** (the predicted address, the calls, and the Safe nonce read from the Safe; the safe.wei gateway under Advanced), **Done** (the safe.wei link for the owners, after the deployment's progress on the wallet path). A modifier deployed but not yet enabled reopens the wizard at Review.

Open a Safe and select Create to deploy Roles 2.1.1. Owner, avatar and target default to the Safe. Advanced settings expose the uint256 salt. Before offering any transaction, roles.wei computes the CREATE2 proxy address locally, checks that the mastercopy and factory exist, rejects collisions, and compares the result with the factory’s own simulated return value.

The recommended option creates a single atomic Safe batch: deploy the proxy and enable that exact predicted address. The alternative sends only the deployment from the connected wallet, verifies the receipt, runtime and three settings, then prepares a separate Safe enablement link. A separately deployed proxy is shown as “awaiting Safe enablement” on later visits; it cannot use the Safe’s assets until the owners approve that second transaction.

Connected, enabled role members see Use this role. Paste the target’s JSON ABI or one or more human-readable function signatures. roles.wei lists only active role targets and, for function-scoped targets, only ABI selectors that the role permits. Choose a function, type each ABI value, the Safe value in wei and CALL or DELEGATECALL. Arrays and tuples use JSON array syntax.

Simulate sends the exact `execTransactionWithRole` wrapper through `eth_call` from the connected member with `shouldRevert=true`; it requires the returned success flag as well as a successful RPC response. The review shows the role, function, parsed arguments and target calldata. Send rebuilds and re-simulates the wrapper immediately before asking the wallet. The wallet transaction always sends zero ETH to Roles: the value field describes funds the Safe will send to the target.

Edit conditions starts from a supplied target ABI, so every comparison follows the function’s real type structure. Pick a write function and execution options, then constrain scalar leaves with Pass, equality, avatar equality, unsigned greater/less, an exclusive two-bound range, one of two values, or an allowance. Nested tuples are matched field by field; dynamic arrays apply the selected element condition to every item; fixed arrays are represented as their exact inline tuple shape. The browser editor limits fixed arrays to 64 items so an accidental ABI cannot create an unusable form.

Transaction allowances optionally constrain total ETH value or the number of calls. Condition values are ABI encoded locally, role/allowance names become exact bytes32 keys, and the generated breadth-first tree is checked against the pinned Roles 2.1.1 `Integrity.sol` and `Topology.sol` rules before it enters the pending diff. The validator checks root resolution, operator/type/value combinations, child counts, BFS parents and compatible logical/array type trees. Contract-backed tests cover nested tuples, dynamic bytes, dynamic arrays and fixed arrays.

Wallet rejection, insufficient gas funds, unavailable history and unsupported RPC methods are described with a next step. Disconnecting returns an address route to the connection gate without losing it, and an address on a different chain opens a switch-chain gate before any reads.

For production, see [Deploying roles.wei](deploy.md). The deploy script and browser-wallet LAN deployer both derive the immutable CREATE2 addresses from the exact built page, skip completed steps and verify `html()` byte for byte. Only the name owner performs the mainnet deployment and points `roles.wei`.
