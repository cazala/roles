# Guide

Run `npm ci && npm run build` to create `dist/index.html`. Run `npm run fork` with an archive-capable `FORK_URL`, then `npm run dev -- --anvil http://127.0.0.1:8545` to use the development-only Anvil wallet. The normal `npm run dev` has no test wallet. Never use Anvil's public test keys with real funds.

Home, once you have opened something, is your saved Safes and Roles modifiers under one field that searches them (by address or label) or opens a new one: paste a 0x address or a `.eth` / `.wei` name and an Open row appears (Enter opens it). Each row opens as a whole; its network shows only when it differs from your wallet's (or, with no wallet, when they are on several); hover (always shown on touch screens) to **Rename** it in place (the name is its label, used everywhere) or remove it from the list, with Undo. **+ New** creates a Roles modifier: pick the Safe it is for (your saved Safes are suggested, not your modifiers; roles.wei remembers which is which when you open them, and checks older entries onchain), and its page opens the create wizard. The ▾ next to it holds **Labels** (every label in this browser, newest first or by name; add, edit, remove with Undo), **Backup & sync** (export your saved addresses, labels and contract ABIs as a link or JSON, or import one, from roles.wei or safe.wei, with a preview and Merge or Replace; your RPC endpoints and block explorer keys are never included) and **Settings** (below). On the first visit, the page explains roles.wei with an Open field and **New to Roles? Create a modifier** (the same as + New), and links to Import a backup, Labels and Settings. Opening an address: it opens at its URL (`#/<address>`), and if it needs something first, the page says so, as in safe.wei. Without a wallet it asks you to connect one (one button per wallet found; with just one, a fresh Open connects it right away), then opens the address. When the link names a chain (`?chain=`, as saved addresses open) and your wallet is on another, it offers **Switch to …**. An address you saved only on another chain may exist on this one too, so it offers the switch and **Open it on … anyway**. A name opened on another chain offers Ethereum, where names resolve. **Settings** (home → ▾, the cog) holds the safe.wei gateway (below) and two optional things, kept in this browser: **RPC endpoints**, where every read on an endpoint's chain goes instead of your wallet's RPC (paste a URL such as Alchemy or Infura; its chain is detected; signing always stays in your wallet), and the **Block explorer** whose index serves a modifier's history in a few requests, and contract names: **Default** (Blockscout, then Routescan, on the chains they cover; built into the page), **None** (everything through your RPC), **Etherscan** (needs a free API key; its free plan covers only some chains), **Blockscout**, **Routescan** (keys optional), or **Custom**, any Etherscan-compatible API URL with `{chain}` for the chain ID. Picking one applies at once (✓ Saved); Etherscan without a key, or Custom without a URL, waits for its field and **Save** (or Enter), and until then the previous choice stays in effect. The key field is named after your choice; the line under it lists the chains it covers. roles.wei checks each event against the chain, but trusts the explorer to return all of them: a missing event would hide a permission. When the explorer does not cover the chain (or your plan does not), or is busy, the history reads through your RPC instead and the status says so. Connect your browser wallet when prompted, or **WalletConnect** to use a wallet on your phone: scan the QR code with the wallet app and approve; signatures and transactions are then confirmed on the phone, and the account menu offers **Switch to …** for every network the phone approved. The account button shows the chain and your account, by its .wei or ENS name when it has one (Ethereum); its menu has Switch wallet and Disconnect. Names use only onchain resolution through the wallet. Label addresses with the tag button; Remove has a local Undo action. Saved entries remember their chain.

Opening a Safe lists its enabled modules. Open a supported Roles 2.1.1 proxy to scan its history and inspect roles, members, targets and raw conditions. Under the history status (and, when there are any, a link's proposal and the pending changes, which concern the whole modifier), one row of tabs switches what is right below it: **Roles · N**, **Members · N** and **Allowances · N**, with the open tab's action on the right (+ New role, + Add member, + New allowance). **Roles** is a row per role with the targets it touches by name (your label, else the contract name from your ABI or the block explorer, else the token symbol read from the contract, else the short address; the first three, then +N) and its member and target counts. **Members** turns it around, a row per member with its roles as chips (the default one marked default: calls that name no role use it) and Disabled when it is not enabled, answering what an address can do. In the editor, **+ Add member** (next to the tabs there) and a member's ⋯ → Edit roles… set every role it is in at once, with checkboxes, and its default role; the ⋯ also has Copy address and Remove from all roles, which leaves it struck through in place with Restore until applied. A search over roles, members and targets appears once there are more than a few. The scan runs in bounded windows, caches completed work, keeps going until it catches up, and can be paused and resumed. It needs no archive RPC: the start is the modifier's deployment block, found from its code at past blocks where the RPC keeps them, else from its `RolesModSetup` event (emitted once, when it is deployed), which is in the logs every node keeps. ⋯ → Start from block accepts a start block; a history that contains the setup event is complete, and one that starts after it is explicitly read-only. ⋯ → Clear cached history discards cached events and scans again. Faulty and unknown versions remain identified without editing. All deployment/name changes on mainnet belong to the owner. When your wallet's RPC does not keep that history (errors like "historical state … is not available" or "pruned history unavailable"), the scan continues through WalletConnect's RPC, and the status line says which RPC served it. What was read is kept in this browser: the events scanned so far (the next visit only reads new blocks) and the modifier's deployment block, which never changes (it survives clearing the cached history). If the chain reorganized the latest blocks, only the last 1,000 blocks are scanned again. The history shows as one sync bar: the status, then the one action that fits it (Pause while scanning, Resume when paused, Retry after an error, Refresh when done), with a thin progress line while it scans; ⋯ holds the rare options, Start from block and Clear cached history. Once the history is complete the bar recedes to a muted line. While it scans, the status shows the share of blocks done, the events found and a time estimate from the scan's own pace; when no block explorer serves the chain, it ends with **Slow? Use Blockscout’s index** (or the explorer that covers the chain; it opens Settings), since the history then loads in a few seconds. Through an explorer, each refresh also reads the last 128 blocks again, since an explorer can index the newest blocks a little late: a change applied minutes ago always shows up.

A role's page keeps the modifier's tabs above it, with their counts. Under the role's name and key, its **members** sit on one line, each with its chips (Default role, Disabled) and, when editing, its ⋯ (Make this their default role, Copy address, Remove member), then **+ Add member**. **Permissions · N** follows, with **+ Add target**: one card per target contract (its name, full address and clearance: All functions, Scoped · N functions, or Revoked; the name is your label for the contract if you set one, with the tag next to the address, else its name from your ABI or the block explorer, which then stays next to the address) listing each allowed function with its signature, its selector, and warnings when it may send ETH or delegatecall. Conditions read as a table, one row per parameter (Parameter · Type · Condition · Value), with AND / OR / NOR groups drawn as labelled brackets, nested tuples and arrays indented, allowances linked, and parameters without a condition shown as any value. Names come from an ABI you give (the card's ⋯ → **Add contract ABI…**: **Upload .json**, a compiler artifact from Hardhat, Foundry or Truffle, or a plain ABI, or paste it; the contract name comes from the artifact or the optional name field; the option is hidden when the block explorer already has the verified ABI), else the block explorer's verified source (the contract name too, a proxy's merged with its implementation's; the card says when the explorer has no verified source), else standard interfaces (ERC-20, ERC-4626, WETH); a name is used only when it matches the function's selector, which is what executes, and the card says where the names came from. Values are decoded by the ABI type when known, otherwise shown exactly as encoded; with an Etherscan key, addresses (in values and in Members) show the contract's name next to them, muted (e.g. GPv2VaultRelayer, or SafeProxy for a Safe); A function's ⋯ → Exact conditions shows the conditions exactly as stored (the flat list the contract checks), with Copy. Unknown operators remain explicitly raw. Without a supplied ABI, parameters are numbered and comparison values stay in their exact encoding; the app never guesses token units or parameter names. The Allowances tab has one card per allowance, read as a sentence: what is available now (the stored balance accrued to the displayed block, as the contract does), how much it refills every period and its cap, when the next refill is, and which roles use it and how (a parameter, ETH sent, calls). Amounts are in the unit the allowance counts: ETH for ETH sent, calls for a call count, and for a parameter the target token's own decimals and symbol (read from the contract) when every use is on the same token; otherwise base units, and hovering an amount shows its exact base units. A key that conditions use but that was never set gets a Not set card. In the editor, **+ New allowance** and a card's ⋯ → Edit… ask for the same things in words, each with an ⓘ that explains it: the unit you type in, Available now, One-time or Refills every period, the refill amount, Every (a number and minutes, hours, days or weeks), Never above (the cap; empty for none) and, under Start of the periods, when periods count from (empty: when the change executes). The exact base units show under every amount, and a sentence sums it up as you type. Editing starts from the stored allowance accrued to now. Execution options in the forms explain themselves in an ⓘ too. Once read, a modifier stays in memory for the session, so moving between its roles list, a role and its allowances is instant; the sync bar says when it was read (read 3 min ago). Refresh reads it again, and so do applying changes, clearing the cached history or choosing a start block, changing Settings, and another wallet, account or chain. Drafts are kept across these pages.

Complete scans are editable, in place: each thing carries its own actions. On a role's page, **+ Add member** ends its members line and **+ Add target** sits next to Permissions. A target card's ⋯ has Add function, Allow all functions (or Execution options and Only configured functions when it allows all), the contract ABI, Copy address and Revoke target; **+ Add function** at the bottom of a scoped card lists the contract's write functions from its ABI (yours or Etherscan's) that the role does not have yet, to allow with any parameters or with conditions, or takes a typed signature or selector. The address fields in Add target and Add member suggest your labelled addresses: all of them when the field is focused (the list scrolls past six), filtered by label or address as you type, picked with a click or the arrows and Enter, and the picked address shows its label; addresses already in the role are left out. Click a parameter's row in a condition table (or a function's ⋯ → Edit conditions, or **Add conditions** under Any parameters) to edit it: the editor opens on that function with its current conditions filled in (Any value, Equal to, One of these values with any number of them, Between, Greater or Less than, Equal to avatar, Within allowance, and the transaction allowances), scrolled to that parameter, so saving changes only what you change; a condition it cannot express (a bitmask, a custom check, a nested structure of another shape) is kept exactly as stored and marked so, unless you choose to replace it, and when the whole tree has a shape it cannot read it says so and starts from Any value. A function's ⋯ has Edit conditions (typed from its ABI; number values are typed with a unit, base units, the target token's own units when it answers decimals(), gwei, ether, ×10⁶ or ×10⁸, and the exact base units they become show under the field), Allow any parameters, Execution options and Revoke function; a member's ⋯ has Make this their default role, Copy address and Remove member. What the draft changes is marked where it is: New or Changed on the card or row, and a revoked target, function or removed member struck through in place with **Restore**. One bar above the role counts the pending changes, with Undo, Discard and **Review changes**, which lists the calls before applying them. Review changes shows the modifier and its chain (by name, else its chain ID), then the calls in the order they apply, one numbered card each: the action, a Widens access tag where it does, and its parameters read by type (full addresses, the target's contract name and the function by its selector from the target's names, role keys by name, execution options in words, conditions collapsed to their count), with the signature and calldata under Calldata. **Copy changes**, next to Apply or Prepare safe.wei link, copies every call as plain text (modifier, chain, owner, then each call's action, signature, parameters, `to` and calldata) to paste to a reviewer, a person or an agent. Widening permissions and authority changes carry explicit warnings. Drafts stay in this browser until they are applied or discarded, and Undo restores the preceding draft state.

When the modifier owner is the connected account, Apply sends each configuration call separately after simulating it and checking that the onchain configuration has not changed. Each receipt updates the baseline, so an interruption preserves only the calls that remain. When a Safe owns the modifier, Review changes prepares the verified `#tx=` link as soon as it opens (with the current nonce and your gateway; Safe hand-off options change either, and the link is prepared again), then shows one row: **Open in safe.wei to approve**, **Copy link** and **Copy changes**. The app validates the Safe transaction hash returned by the Safe and includes each readable call signature; copy the link or open it for the owners to review and approve in safe.wei.

If the owner is neither the connected account nor a readable Safe, roles.wei says so before editing. The generated configuration calls remain fully inspectable in Review changes, but the app does not pretend it can submit them for an unknown owner. On narrow screens, a fixed pending-changes button stays above the browser edge until the draft is reviewed or discarded.

Creating a modifier is a four-step wizard, one step at a time with Back / Next: **Setup** (owner, avatar and target are this Safe, recommended; Customize to change them, with a warning for anything else; the salt under Advanced), **How** (with the Safe in one transaction, recommended, or deploy now from your wallet and enable later), **Review** (the predicted address, the calls, and the Safe nonce read from the Safe; the safe.wei gateway under Advanced), **Done** (the safe.wei link for the owners, after the deployment's progress on the wallet path). A modifier deployed but not yet enabled reopens the wizard at Review.

Open a Safe and select Create to deploy Roles 2.1.1. A Safe without a working Roles modifier shows the Create card above its modules; one that already has one (not a faulty version) shows only a quiet **+ Create another Roles modifier** link under them. Owner, avatar and target default to the Safe. Advanced settings expose the uint256 salt. Before offering any transaction, roles.wei computes the CREATE2 proxy address locally, checks that the mastercopy and factory exist, rejects collisions, and compares the result with the factory’s own simulated return value.

The recommended option creates a single atomic Safe batch: deploy the proxy and enable that exact predicted address. The alternative sends only the deployment from the connected wallet, verifies the receipt, runtime and three settings, then prepares a separate Safe enablement link. A separately deployed proxy is shown as “awaiting Safe enablement” on later visits; it cannot use the Safe’s assets until the owners approve that second transaction.

Connected, enabled role members see Use this role. Paste the target’s JSON ABI or one or more human-readable function signatures. roles.wei lists only active role targets and, for function-scoped targets, only ABI selectors that the role permits. Choose a function, type each ABI value, the Safe value in wei and CALL or DELEGATECALL. Arrays and tuples use JSON array syntax.

Simulate sends the exact `execTransactionWithRole` wrapper through `eth_call` from the connected member with `shouldRevert=true`; it requires the returned success flag as well as a successful RPC response. The review shows the role, function, parsed arguments and target calldata. Send rebuilds and re-simulates the wrapper immediately before asking the wallet. The wallet transaction always sends zero ETH to Roles: the value field describes funds the Safe will send to the target.

Edit conditions starts from a supplied target ABI, so every comparison follows the function’s real type structure. Pick a write function and execution options, then constrain scalar leaves with Pass, equality, avatar equality, unsigned greater/less, an exclusive two-bound range, one of two values, or an allowance. Nested tuples are matched field by field; dynamic arrays apply the selected element condition to every item; fixed arrays are represented as their exact inline tuple shape. The browser editor limits fixed arrays to 64 items so an accidental ABI cannot create an unusable form.

Transaction allowances optionally constrain total ETH value or the number of calls. Condition values are ABI encoded locally, role/allowance names become exact bytes32 keys, and the generated breadth-first tree is checked against the pinned Roles 2.1.1 `Integrity.sol` and `Topology.sol` rules before it enters the pending diff. The validator checks root resolution, operator/type/value combinations, child counts, BFS parents and compatible logical/array type trees. Contract-backed tests cover nested tuples, dynamic bytes, dynamic arrays and fixed arrays.

Wallet rejection, insufficient gas funds, unavailable history and unsupported RPC methods are described with a next step. Disconnecting returns an address route to the connection gate without losing it, and an address on a different chain opens a switch-chain gate before any reads.

For production, see [Deploying roles.wei](deploy.md). The deploy script and browser-wallet LAN deployer both derive the immutable CREATE2 addresses from the exact built page, skip completed steps and verify `html()` byte for byte. Only the name owner performs the mainnet deployment and points `roles.wei`.

The footer links to safe.wei and to the source code. Links to safe.wei (the footer, and Safe transaction hand-offs unless you typed another gateway in Safe hand-off options) use the gateway on the same family as this page: roles.caza.la → safe.caza.la, roles.wei.is → safe.wei.is, roles.wei.limo → safe.wei.limo, else the first (safe.caza.la). These links are in the config chunk (`config/links.json`), so changing them redeploys only that chunk. Settings → **safe.wei gateway** picks another one (the built-in gateways, or Custom… for your own https URL), kept in this browser; it is the same setting as the gateway in Safe hand-off options.

A **draft link** (`#/<modifier>?chain=<id>&draft=…`, [links.md](links.md)) proposes permission changes: opening it loads them into the editor as pending changes, marked where they are, under a banner that says the link proposes them, shows the link's note as unverified and lists them in words (What the link asks for). Check them like your own edits; nothing happens onchain until you review and send them. With changes already pending, it asks first: Add to them, or Start fresh with only this link (Undo brings yours back). A link that cannot be read loads nothing and says why; on a partial history, it is not loaded.
